# 奇趣小岛｜整体开发路线图

- 文档版本：V1.0
- 文档用途：作为整个项目的开发总纲；后续每次只推进一个阶段，并按验收结果决定是否进入下一阶段。
- 项目类型：面向中国大陆 6–8 岁儿童的轻探索、轻任务、收集、建造与装饰手游。
- 开发原则：小步交付、先验证核心玩法、控制范围、保护既有文档与用户改动。

## 当前项目判断与产品方向（2026-10-27）

**产品方向：**把《奇趣小岛》做成一款温暖、低压力的 2D 岛屿修复与装饰游戏。玩家探索小岛、帮助动物完成短任务、收集并摆放物品，让环境出现看得见的变化。主线要有一个清楚的庆祝结尾；结尾之后仍可完成支线并自由探索。它不以复杂经营、战斗或付费系统为目标。

**玩家循环：**看懂一个当前目标 → 在岛上探索并互动 → 收集、拖拽或建造 → 看到岛屿和伙伴发生变化 → 收到简短反馈并得到下一个目标。对 6–8 岁玩家，任何时刻都应突出一个当前任务和一个直接的下一步；完成反馈短暂显示，已解锁区域、旧对话和未使用的空槽不应继续占据注意力。

**当前真实进度：**项目已从环境搭建进入可玩灰盒原型。Godot 4.7.2、浏览器预览和自动化回归链路已建立；Q001–Q006 主线建造、Q012 庆祝结尾和 Q007–Q011 结尾后支线已连通；72 项自动化套件覆盖状态、运行时输入和存档迁移。已用全新浏览器存档通过真实按键和拖拽走完 Q001–Q012，再从主线完成存档真实操作走完 Q007–Q011；浏览器检查覆盖种下种子后的狐狸引导、乌龟花园、支线绿框拖放、终局、建造调整和刷新存档。任务提示与触控布局修订已完成；美术与动画进行了三轮小步统一，包含角色和交互反馈、环境动效、岛岸与动物造型细节。当前待用户检查网页效果；目标玩家试玩仍待安排。正式美术资产、目标平台和真实试玩也尚未确定，因此项目仍是灰盒原型。

**本轮已完成：**种下种子后，兔子会接着提示玩家去帮狐狸收集 3 份木材；狐狸入住后兔子暂时退场，直到主线庆祝时再出现。主线 HUD 现在显示 1/7 至 7/7 步数，结尾后的五项支线显示“可选 1/5 至 5/5”；每段底部提示只写当前操作，乌龟花园拆成浇水、收集、摆放三个连续步骤。额外地块放满 3 件物品后，整理入口会关闭、已布置场景保留，终局明确显示“没有必做任务”，并把建造调整和自由探索作为可选去向；进入建造调整时也会说明如何移动或收回已摆放装饰。鸟屋问候和新花回访也明确标为可选。Q006 装饰首次完成后会引导玩家回兔子处触发 Q012，结尾后开放 Q007–Q011。已用真实浏览器输入走完贝壳、鸟屋材料与问候、种子收藏、石板铺路和额外地块整理；检查发现 Q008 路面拖拽缺少绿色目标提示，现已补上所有空槽的绿色可放提示和悬停高亮。Q010 完成后，旧鸟屋和种子任务卡会收起，避免遮挡当前的铺路目标；所有任务完成时也会去掉与最终目标重复的短暂提示。本轮把四向按钮改为可拖动圆形虚拟摇杆，互动按钮移至右侧，并把额外地块从狐狸小屋下方移至左侧空地；底部增加“现在做什么”提示，明确互动按钮所在位置。摇杆支持鼠标、单指触控、方向限幅和多指隔离；浏览器窗口较宽时，右侧按钮会跟随屏幕边缘，超出 16:9 的区域用海天背景延伸补齐。72 项回归、主线及支线浏览器流程、摇杆触控逻辑、拖拽高亮、刷新存档和 WebGL2 不可用提示均纳入检查。

**本次反馈修复：**常用“收集 / 互动”按钮已移到右下角大拇指区域，并随实际画布大小贴边；乌龟花园现在必须先浇水，浇水前采花和摆放都会被状态层拒绝，花苗也会显示为待浇水状态。蓝花种子已从兔子附近移到空地，并加入不重叠检查。额外地块整理尚未开始时，右下角也会预览三件可整理物品，右上角绿色按钮明确显示“开始整理”，顶部进度和底部操作提示会说明先后步骤。Web 预览增加了 1630×870 宽屏与 844×390 横屏检查；浏览器已实际走通 Q007–Q011 并验证刷新后保留进度。

**第五轮流程闭环与摆放交互（2026-10-27）：**乌龟花园调整为“浇水 → 逐株采收三朵花 → 回乌龟处交付花束”，采花后植株留在花圃，不再要求把刚采下来的花苗拖回原处；任务完成后收起“待采 / 已浇水”等旧标签，避免后续装饰时遮挡。池塘可互动并触发水纹与乌龟反馈，乌龟也会在身边回应。花园装饰现在可在右侧岛屿草地任意合适位置摆放或移动，绿圈提示可放位置，池塘、乌龟、花圃和彼此重叠的位置会被避开，坐标即时存档。散落材料收齐后要到鸟屋旁逐件交付，鸟屋按交付数量逐步搭建；每块池塘石头和每件装饰都会显示进度及短暂转场反馈。额外地块整理入口点击前不显示托盘和空槽，点击“开始整理”后才进入操作。主线最终一步会明确提示走到兔子身边点“庆祝”，庆祝期间突出完成状态并暂时收起支线物件。已通过 72 项 GDScript 回归、Q001–Q012 主线浏览器流程、Q007–Q011 支线浏览器流程、真实网页自由移动装饰与刷新存档检查；WebGL2 可用性和浏览器控制台也通过。本轮网页截图留在 `tests/artifacts/web-q005-bouquet-delivered.png`、`tests/artifacts/web-q006-free-placement-after.png`、`tests/artifacts/web-q009-birdhouse-under-construction.png`、`tests/artifacts/web-q011-before-start.png`、`tests/artifacts/web-q011-after-start.png` 和 `tests/artifacts/web-q012-after-interact.png`。当前停在本轮验收节点，等待用户检查网页效果。

**本轮美术与动画：**继续使用现有柔和扁平矢量绘本画风，不混入风格突兀的新素材。兔子、狐狸和乌龟增加轻微待机起伏与眨眼，玩家移动时增加步伐起伏；收集、放置、浇水会出现短暂闪光，浇水后花苗从小到大长出，桥梁修好时扫过一束亮光，主线结尾出现短暂彩纸庆祝。效果均由对应游戏状态触发，不改变任务规则。72 项回归、浇水与采花浏览器流程、主线和支线完整浏览器流程、WebGL2 及控制台检查通过；下一步由用户看网页效果后反馈是否自然、清楚。

**第二轮环境动效：**在保留场景布局和任务目标位置的前提下，让河流波纹与水面高光缓慢移动，池塘水纹轻微起伏，云层和草叶随微风变化，花圃幼苗轻轻摆动。浏览器截图的河流区域在 1.2 秒间发生了 5,615 个像素变化；完整主线、支线与 WebGL2 浏览器检查均通过，72 项本地回归也通过。

**第三轮风格统一：**岛屿增加沙岸内外层和稀疏花簇，动物补上更清楚的身体与面部细节，玩家小角色有了背包、耳鼻和表情，狐狸小屋补上窗户和屋檐线。花簇只放在边缘空地，任务物品、文字、碰撞与交互位置保持不变。72 项回归及完整浏览器流程通过，主线开始、乌龟花园和结尾画面已人工检查。

**第四轮触控与界面分区：**右下角互动按钮扩大到 116×92，并根据当前附近目标显示“收木板、浇水、采花、收木材、交木材、庆祝”等动作；进入只需拖拽的摆放和铺路步骤后，按钮会暂时收起。物品托盘移到指引条上方，与按钮保留独立触控区域；石板、木板、幼苗和整理物品槽位同步调整。指引文字改为提示“点右下角按钮”，避免按钮名称变化后提示过期。72 项 Godot 回归及完整浏览器流程已通过；检查覆盖主线互动、Q007–Q011 支线拖拽、刷新存档、WebGL2 和 1280×720／844×390 两种画面。

**接下来的开发顺序：**

1. 先让用户检查第四轮的互动按钮、托盘分区和触控画面，以及任务流程提示；收到反馈后修复并重走浏览器流程。
2. 验收后继续美术与反馈阶段，逐步统一角色造型、装饰细节、声音提示和场景层次；保持每次改动可单独预览、可回归。
3. 美术和交互稳定后开展目标年龄试玩，再决定首发平台和发行清单；证据不足时不宣称具备发行条件。

## 三、每个阶段的统一工作流程

```mermaid
flowchart TD
    A[确定一个阶段目标和验收标准] --> B[检查代码、文档、工作区和依赖]
    B --> C[实施当前阶段的改动]
    C --> D[运行自动化测试并在浏览器真实操作]
    D --> E{阶段验收通过？}
    E -- 否 --> F[修复问题并重跑相关测试] --> D
    E -- 是 --> G[更新路线图并提供网页、截图和验证结果]
    G --> H[暂停，等待用户检查本阶段]
    H --> I{用户反馈}
    I -- 发现问题 --> F
    I -- 确认没问题 --> J[进入下一个阶段]
    J --> A
```

### 每轮 Codex 任务必须包含

1. **本轮目标**：只写一个阶段目标或一个可独立验收的小任务。
2. **先检查再计划**：先阅读相关代码、配置、文档和当前工作区状态。
3. **修改边界**：列明允许修改的文件/模块，以及明确禁止碰触的部分。
4. **验收标准**：写成可以验证的结果，而不是“看起来没问题”。
5. **验证范围**：只运行与改动相关的必要检查；如果测试/构建成本高，先说明原因与方案。
6. **结果报告**：改了什么、如何验证、结果如何、还剩什么风险。
7. **阶段门禁**：未达到验收标准时，不宣称阶段完成；通过后提供可直接查看的浏览器结果并暂停，等待用户检查。用户反馈问题时修复当前阶段；用户确认后才开始下一个阶段。

## 四、阶段 1 交付记录：开发环境与技术方案落地

本节保留初始环境阶段的验收依据。该阶段现已完成，当前迭代按上方“当前项目判断与产品方向”推进。

### 任务 1：检查项目与文档

- 阅读 `docs/` 下的立项说明书、GDD、MVP 开发规格与技术方案、AI 开发提示词、测试与儿童安全清单。
- 检查当前目录、现有代码、引擎版本、依赖和已有改动。
- 标记文档冲突、缺失决策和不应由 AI 自行猜测的内容。
- 不覆盖或删除用户已有文件，不因“整理”而重写已确认的产品决定。

### 任务 2：确定技术选择

- 若尚未选定引擎，优先评估 Godot 4；如果开发者已熟悉 Unity，则基于实际熟悉程度、目标平台和导出要求做比较后再定。
- 明确首发目标设备/操作系统、屏幕方向、输入方式、最低性能目标。
- 明确资源格式、场景组织、存档方案和版本控制规则。
- 发行平台、商业化和合规要求只记录待核实项，不在证据不足时假定已满足。

### 任务 3：搭建最小可运行项目

- 创建清晰、不过度设计的目录结构。
- 建立启动场景、基础输入、简单占位画面和错误日志机制。
- 确保项目能启动、能调试、能导出一个最小构建。
- 暂不开发完整地图、任务系统、正式美术、广告、内购、联网、账号或多人功能。

### 任务 4：形成技术基线记录

至少记录：
- 引擎与版本、语言、开发环境和导出目标；
- 项目目录职责；
- 启动、运行、调试、导出步骤；
- 当前已验证事项和未验证事项；
- 已知风险及后续处理方式。

## 六、验收与问题优先级

- **P0 阻断**：无法启动、存档丢失、主要流程无法完成、严重安全或隐私风险。必须修复后才能通过。
- **P1 重要**：核心交互不清楚、任务无法完成、频繁卡顿或关键设备适配问题。原则上在阶段验收前修复。
- **P2 一般**：局部视觉、动画或不影响核心流程的小问题。记录后按成本和收益排期。
- **P3 优化**：非必要扩展和锦上添花的改进。默认不阻塞当前阶段。

每个问题都记录：复现步骤、预期结果、实际结果、影响范围、优先级和验证结果。

## 八、项目执行规则

- 一次只推进一个阶段；每个阶段拆成小任务。
- 范围清楚且可逆的任务，直接实施并自行验证；每个阶段验收通过后都交付网页和结果，停下来等待用户检查。
- 不猜测业务规则、外部接口、平台要求或未确认的技术决策。
- 不做与当前任务无关的重构，不因局部任务重写整体架构。
- 不覆盖用户未提交的修改，不执行未获授权的破坏性操作。
- 默认不执行 Git 写操作（包括 commit、push、pull、fetch、merge、rebase、checkout、switch、reset、stash、branch）；如确有需要，先单独征求用户确认。
- 每次完成后更新阶段状态和决策记录；阶段通过后等用户验证，收到“没问题/继续”后再按路线图开始下一阶段。
