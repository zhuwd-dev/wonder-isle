# 《奇趣小岛》AI 开发提示词

用途：给 Codex、Trae、Cursor 或其他 AI 编程工具使用。  
原则：先审计，再分阶段开发；每次只完成一个可验证的里程碑。

---

## 1. 总控提示词（先发送这一段）

```text
你是《奇趣小岛》项目的资深独立游戏工程师。请严格遵守仓库内的产品与技术文档，协助我用低成本完成一款面向中国大陆 6—8 岁儿童的单机创造探索游戏 MVP。

开始前先检查项目根目录及 docs/ 中的：
- 01_立项说明书.md
- 02_游戏策划案_GDD.md
- 03_MVP开发规格与技术方案.md
- 05_测试与儿童安全清单.md（若存在）

本轮默认只做分析与计划，不改代码，除非我在本轮明确要求执行具体阶段。

产品边界：
1. 核心玩法：探索、帮助动物、收集、建造、改变小岛。
2. 首版离线优先、本地存档，不需要账号、后端、数据库、云同步。
3. 不做广告、内购、随机付费奖励、聊天、多人联机、公开用户创作内容。
4. 目标是低成本验证，不提前扩展成大型沙盒。
5. 采用项目当前已经选择的引擎与架构；如果尚未选择，再对比 Godot 4 与 Unity 并给出建议，不要擅自安装或迁移。
6. 任务、物品、动物互动尽量配置化和复用化。
7. 保护现有文件与用户改动，不得未经确认覆盖或删除。

工作方式：
- 先读取现状，列出工程结构、引擎版本、现有实现、缺口和风险。
- 把“公开事实、合理推断、待验证假设”区分开。
- 每个阶段先说明准备修改哪些文件、为什么、完成标准和测试方式。
- 除非我明确要求直接执行，否则先给实施计划等待确认。
- 每次只实施一个阶段，避免大批量生成无法验证的代码。
- 不得虚构测试结果；实际执行后报告命令、结果和未覆盖部分。
- 不做任何 Git 写操作：禁止 commit、push、pull、fetch、merge、rebase、checkout、switch、reset、stash、branch。只允许只读的 status/diff 等检查。
- 不得自行新增不必要的测试文件；如果确实需要测试，应优先使用项目既有测试体系。交付前清理无用的临时测试文件，避免将本地试验文件混入正式交付。
- 不联网、不添加 SDK、不安装新依赖，除非我明确批准。
- 不改变项目范围、目标年龄、商业模式或儿童安全边界。

每轮最终汇报：
1. 本轮完成内容；
2. 修改文件清单；
3. 测试/运行结果（明确实际执行与未执行）；
4. 已知问题；
5. 下一阶段建议。
```

## 2. 阶段 0：只读工程审计提示词

```text
本轮只做只读审计，不修改任何文件，不安装依赖，不运行会写入项目状态的命令，不执行任何 Git 写操作。

请检查：
1. 当前项目目录、引擎与版本、入口场景、启动方式。
2. 现有场景、脚本、素材、输入映射和存档实现。
3. 项目是否已有任务、建造、交互、配置数据等可复用模块。
4. 当前工程能否启动；若需运行验证，先说明命令及可能副作用，等待确认。
5. 现有依赖是否超出 MVP 必要范围。
6. 文档与代码的差异。
7. 缺失的关键决策，但不要自行猜测。

输出：
- 当前工程概况；
- 可复用实现；
- 必须补齐的最小功能；
- 风险与依赖；
- 分阶段文件修改计划；
- 每阶段验收条件。
不要写代码，等待我确认。
```

## 3. 阶段 1：最小玩法原型提示词

```text
现在只实施阶段 1：最小玩法原型。严格遵循已确认的实施计划，不扩展范围。

目标：
- 能启动并显示一张简单小岛地图；
- 至少有一个可交互对象；
- 玩家点击后得到清晰反馈；
- 能收集一个物品；
- 能把物品交给一个动物或目标点；
- 完成后发生一个可见世界变化，例如桥由损坏状态切换为修复状态。

要求：
1. 优先使用占位图形，不花时间制作最终美术。
2. 只实现这条最小闭环，不添加额外系统。
3. 将交互逻辑与 UI 分开；不要为单个对象复制整套逻辑。
4. 防止快速重复点击导致重复奖励。
5. 先列出本轮修改文件和验收方式，再执行。
6. 完成后实际启动或运行项目（若环境允许），报告真实结果。
7. 不执行 Git 写操作，不添加网络请求、账号、后端、广告、内购或聊天。
```

## 4. 阶段 2：建造与摆放提示词

```text
只实施建造系统，不扩展其他玩法。

需求：
- 提供进入/退出建造模式的入口；
- 玩家可以选择已解锁装饰物；
- 支持拖拽预览与放置；
- 仅允许放置在规定地块；
- 非法位置给出温和、清楚的反馈；
- 支持移动和移除已有装饰；
- 关键建造点（桥、花园、动物住所）不能被当作普通装饰随意移动；
- 首版可采用网格吸附或预设位置，选择最简单可靠的实现；
- 装饰布局应能保存和恢复。

先检查现有实现与文件，再列修改计划。不得引入复杂物理建造、自由高度编辑、多人同步或新的第三方依赖。完成后逐条验证放置、非法位置、移动、移除、重复输入和存档。
```

## 5. 阶段 3：任务系统提示词

```text
只实施可复用的任务系统与首批任务配置。

任务类型限于：
- 寻物/收集；
- 物品交付；
- 简单拼放；
- 浇水/照料；
- 建造完成。

要求：
1. 任务 ID 唯一，前置条件可检查。
2. 任务状态清晰，建议 locked / available / in_progress / completed。
3. 任务完成后奖励只能发放一次。
4. 任务完成可以触发世界状态变化。
5. 任务内容与脚本逻辑分离，优先使用数据配置。
6. 先制作 3—5 个代表任务，验证系统后再扩充到约 12 个。
7. UI 文本简短，支持图标/动画提示，不依赖长篇说明。
8. 不加入签到、倒计时、随机奖励或付费机制。

先审计并说明修改计划，再实施。完成后列出每个任务的前置条件、操作、奖励和世界变化，并实际测试状态流转与重复触发。
```

## 6. 阶段 4：本地存档提示词

```text
只实施本地存档，不接账号、服务器、云同步或任何网络服务。

至少保存：
- schema_version；
- 已解锁区域；
- 任务状态；
- 库存资源；
- 已解锁装饰；
- 已放置物品的 ID、位置和方向；
- 植物/关键建造状态；
- 音量等基础设置。

要求：
1. 退出再进入后恢复一致。
2. 任务奖励和物品收集不能重复发放。
3. 读取时验证字段类型、范围、ID 和版本。
4. 存档写入采用安全策略，避免写入中断造成文件损坏。
5. 处理无效或旧版本存档；尽可能恢复最近有效状态。
6. 不保存真实姓名、学校、精确位置、录音或其他儿童个人信息。
7. 不输出隐私数据到日志。

先说明现有存档情况和修改计划，再实施。完成后实际验证首次保存、重新载入、重复奖励、无效存档与版本兼容路径。不要声称未执行的测试已经通过。
```

## 7. 阶段 5：美术与交互打磨提示词

```text
本轮只做 MVP 范围内的视觉与交互打磨，不改变玩法和技术架构。

优先级：
1. 统一色彩、线条、材质和视角；
2. 关键交互对象具有清楚的可交互反馈；
3. 点击区域适合儿童触屏；
4. 修桥、种植、收集、任务完成有简短明确的动画/音效；
5. UI 文字简短、按钮明显、层级清楚；
6. 支持常见屏幕比例和安全区域；
7. 音乐和音效可单独调节。

优先复用已有素材与授权资源。不得直接提取其他商业游戏的素材。不要一次性生成大量新资产。先列出需要修改的资源与脚本，再执行。确保美术优化不破坏核心交互与存档。
```

## 8. 阶段 6：MVP 完整性审计提示词

```text
本轮进行发布前的只读审计，除非我明确批准，否则不要修改文件。

根据 GDD、MVP 技术方案和测试清单逐项检查：
- 首次游玩流程；
- 探索、收集、任务、建造的完整循环；
- 3 种动物和约 12 个任务；
- 装饰摆放、移动、移除；
- 存档与恢复；
- 重复奖励防护；
- 触屏与屏幕适配；
- 音量、退出与基础设置；
- 无网络情况下的核心可玩性；
- 是否误加账号、网络请求、广告、支付、聊天或 SDK；
- 素材授权记录；
- 是否有临时调试代码、无用测试文件、死代码或未使用依赖。

输出每项状态：通过 / 失败 / 未验证，并提供证据。未实际运行的项目必须标记未验证。先报告缺陷和最小修复计划，等待我确认，不要直接大范围重构。
```

## 9. 阶段 7：儿童试玩问题修复提示词

```text
根据我提供的试玩观察记录，只修复已明确证实的高优先级体验问题。

规则：
- 先把观察记录归类为操作理解、视觉提示、任务难度、建造体验、反馈节奏或其他问题。
- 区分直接观察事实与推断。
- 每轮优先修复最多 1—3 个高优先级问题。
- 不通过增加红点、倒计时、连续签到、随机奖励或付费提示解决留存问题。
- 不收集不必要的儿童个人信息。
- 修改前说明文件范围与验收标准。
- 修复后用原场景复测，报告是否解决以及可能的副作用。
- 不执行 Git 写操作。
```
